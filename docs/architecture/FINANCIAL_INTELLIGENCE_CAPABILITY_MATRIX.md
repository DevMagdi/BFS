## 2. Partial capabilities and limits

| Area | Implemented portion | Still partial or unresolved |
|---|---|---|
| **Source data** | Manual M14 observation intake and Core Financials general-ledger/bank-activity CSV normalization, explicit source-specific mappings, source-row hashes, and Company-scoped canonical rows. Migration `0023` retains exact original bytes for new Core Financials imports and exposes authorized hash-verified downloads; pre-migration imports remain explicitly unavailable. Cash Flow requires bank activity; P&L measures require general-ledger evidence. | No authoritative connector/authentication, governed source-owner registry, legal retention/deletion schedule, general cross-upload correction chain, or globally governed canonical finance facts. M16 accepts explicit supersession for supported actual movements inside one intake/group. Core Financials rejects duplicate source-record IDs across imports sharing the same Company/source key/type and requires linked exact-opposite reversals under the same policy version. | No universal cross-source financial-event identity or governed correction policy spans M14–M16 and Core Financials. Identical events copied under different source keys or separately hashed source records may not be detected. Supersession and reversal links remain caller/source assertions, not approved accounting policy. |
| **Reconciliation** | M14 compares source-group arithmetic to a caller-supplied control under explicit Decimal tolerances. M11 can compare a trace against a separate expected value and rejects overlapping reference hashes/records/locators. | A distinct reference is not proof of organizational independence, source authority, correct control, or approved accounting meaning. M15 does not treat M14’s control status as independent approval. A failed comparison is not an explanation of cause. |
| **Precision, rounding, currency** | M11 uses bounded Decimal arithmetic and explicit rounding policies; M14/M15 preserve exact text and do not round; M16 uses exact no-rounding arithmetic. Single-group currency rules prevent FX/cross-currency netting. | No finance-owner-approved rounding/display policy, FX source/rate method, cross-currency consolidation, multi-period rollup or currency translation policy. M16 rejects negative cash-flow magnitudes and permits explicit same-group actual supersession. | **Evidence and hashes** | M11/M14/M15/M16 create content hashes and immutable run evidence; M15 and M16 support replay against the same inputs/version. | Hashes are integrity markers, not encryption, source authentication, legal retention, or proof that the original evidence was not replaced before ingestion. | **Analysis and explanations** | M13 provides narrow descriptive comparisons; M11/M15/M16 and Core Financials provide deterministic calculation or replay traces. ## 5. Missing foundations / decision blockers

These are business, source and governance foundations, not problems that can be closed with more code or passing tests alone:

1. A named user, repeated decision/question, domain owner, product scope, decision authority and acceptance baseline for a company-wide business-intelligence capability.
2. Finance/accounting owner(s), authoritative source(s), production access approval, data classification, and an accountable party for source completeness, correction, freshness and retention.
3. A versioned finance fact/transaction model and explicit distinction between accounting records, management-reporting measures, planning assumptions and cash events.
4. Approved revenue/cost/account definitions, effective dates, recognition/cut-off, period-close/restatement, sign, refund/reversal, cross-period correction, and no-double-count policies.
5. Approved currency/FX source and timestamp, units, precision, rounding/display, tolerances and reconciliation control definitions—with independently governed golden examples.
6. Stable cross-source event identity, idempotent corrections/reversals, source population completeness and an approved path for retaining and replaying admissible evidence.
7. M17-ready chronological historical outcomes and evaluation ownership before any forecast/scoring/model-promotion claim.
8. For AI: a named allowed question, authorized/minimized evidence retrieval, on-prem/local inference design if approved, prompt/data-flow policy, grounded-claim evaluation, abstention thresholds, audit and human-review expectations. No AI is implemented here.
9. For production: approved retention/deletion/legal hold, secret custody/rotation, backup/restore, operations, access review and separate customer-data authorization. Synthetic fixtures are not customer evidence or customer performance.
