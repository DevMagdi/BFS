## 1. Executive assessment

**Historical P2-00 recommendation: retain M17 as the bounded technical starting point for AUVRA Predictive Intelligence, but do not treat it as a product-ready forecasting capability.** At assessment time, implementation was to wait for owner decisions. A later Phase 2 owner authorization separately permits sequential synthetic/non-production engineering only; it does not close any human gate. M17 already provides a deterministic, bounded, company-scoped forecast/evaluation record path. Building a second forecasting engine would duplicate useful contracts, evaluation logic, replay, and persistence. M17 is nevertheless a caller-supplied-series prototype: it does not establish the authority, rights, freshness, completeness, or business meaning of its inputs, and it is not connected to an approved real predictive source.

The smallest defensible future shape is **one owner-selected predictive question and one authorized, typed source adapter feeding the existing M17 contract/evaluation path**. Keep the current Python/FastAPI/Pydantic/SQLAlchemy/Alembic/PostgreSQL modular monolith, tenant/company authorization, forced RLS, and evidence/retention controls. Reuse the existing baseline evaluation, versioning, replay, and append-only persistence where they fit. Extend only where an approved source contract or evaluation protocol demonstrates a real gap.

No new forecasting package is recommended now. M17’s three simple baselines are sufficient to establish a reproducible benchmark. A statistical dependency should be reconsidered only if an owner-selected dataset and time-aware backtest demonstrate a concrete limitation that cannot be addressed with the current engine. Statistical libraries bring transitive and native dependencies and generally operate on binary floating-point arrays; neither their numerical behavior nor deployment footprint has been evaluated in BFS.

AUVRA Phase 1 is closed for its accepted Operations-first engineering scope. Phase 2 remains **not started** in the AUVRA roadmap. The existing M17 milestone prototype is not AUVRA Phase 2 acceptance and does not change the four-pillar product strategy. No detailed, owner-approved Phase 2 requirements or predictive use case were found in the reviewed repository. This assessment therefore proposes gates and a candidate sequence; it does not invent a forecast target, source, KPI, metric threshold, business objective, or model choice.

**P2-00 is complete as a historical assessment. ## 2. Scope and governing product boundaries

Operations is the closed Phase 1 proof, not the product boundary. Phase 2 is named **Predictive Intelligence** in the AUVRA roadmap; Phases 3 and 4 remain later, unstarted phases. The product and architecture evidence establishes the following constraints for any eventual forecast capability:

- Use the selected domain and question a Company actually needs; do not presume that every Company needs the same forecast, target, dimensions, frequency, or model.
- Evidence, source assertions, structural validation, deterministic calculations, assumptions, scenarios, predictions, evaluations, recommendations, human decisions, and actions are different concepts. A forecast is not an observed fact, a scenario is not a prediction, a backtest is not production accuracy, and a human review record is not source approval.

## 5. M17 implementation review

### 5.1 What M17 already does and should be reused

The principal implementation is in:

- `src/businessflow/forecasting/contracts.py` — strict versioned request/response contracts and Decimal text inputs.
- `src/businessflow/forecasting/calculation.py` — pure calculation, dataset diagnostics, model evaluation, forecast generation, metrics, and replay validation.
- `src/businessflow/forecasting/models.py` and `migrations/versions/0026_forecasting_engine.py` — versioned Company-scoped data/evaluation/run and reviewer records.
- `src/businessflow/forecasting/service.py` — source/model/protocol integrity, authorization, snapshot/version persistence, evaluation/run replay, and promotion/review operations.
- `src/businessflow/api/forecasting_routes.py` and `src/businessflow/api/forecasting_limits.py` — API routes and transport-body bound.
- `tests/unit/test_forecasting_calculation.py` and `tests/test_forecasting.py` — deterministic calculation/contract tests and PostgreSQL/API control tests.
- `docs/M17_BASELINE_FORECASTING.md` — current supported behavior and boundaries.

M17 supports daily, Monday-start weekly, and first-of-month monthly series, with caller-declared dimensions and per-period decimal-text values or explicit missing reasons. Its only model definitions are:

1. `naive_last_value` — repeat the latest observed training value.
2. `seasonal_naive` — repeat a configured prior seasonal period.
3. `moving_average` — average a configured immediately preceding window.

They are deterministic declarative baselines, not trained statistical or AI models. M17 also provides MAE, RMSE, MAPE, and sMAPE; zero-denominator percentage metrics abstain instead of being filled. Inputs/outputs use Python `Decimal` and technical fixed-scale rendering, not currency rounding or FX.

Validation uses chronological expanding-window rolling origins, with each prediction made only from observations before that block’s origin. Holdout uses one fixed forecast origin and does not fit/calibrate on holdout actuals. A complete validation evaluation may calibrate a holdout or future-run interval; the single holdout is consumed at most once per dataset version. Evaluation keeps the same complete-case scoring sample across candidate models and explicitly reports unavailable predictions/actuals. Outliers are not assessed by default; the optional Tukey-IQR behavior is flag-only and does not remove rows. There is no automatic ranking, champion selection, recommendation, or deployment.

The service has default-off `FORECASTING_ENABLED` and `FORECAST_PROMOTION_ENABLED` settings and blocks operation in `APP_ENV=production` regardless of those flags. Read/write/review permissions are assigned to the existing owner/admin roles; service and database access resolve Company scope from authenticated membership. Promotion is a distinct immutable human decision, requires a reviewer different from the dataset, model, protocol, and evaluation authors, is restricted to non-production, blocks synthetic approval, and records production activation as blocked pending governance.

The dataset route is bounded to 32 MiB at the ASGI middleware boundary; a dataset has at most 20,000 observations and eight dimensions. Calculation budgets cap timeline periods, dense panel cells, evaluation points, rolling-origin blocks, candidate models, and future forecast points. These are engineering resource limits, not minimum-data or business-suitability rules.

### 5.2 M17 gaps and limitations before any product use

| Gap / limitation | Evidence-based impact and required Phase 2 treatment |
|---|---|
| **No source authentication or rights check** | Each record includes a caller-provided source ID/hash/locator/reference, and the dataset origin is caller-declared as `caller_assertion` or `synthetic_fixture`. Hashes bind the submitted snapshot; they do not prove source identity, authority, data rights, completeness, freshness, or permission to process. Require a future domain-owned adapter that independently loads only authorized evidence and records the source checks it performed. |
| **No typed link to an approved source lineage graph** | Source references live inside the M17 input JSON snapshot; M17 does not bind its dataset to Universal Data, M14/M16, M5, or Operations with same-scope source-row foreign keys. A caller can submit internally consistent source references that do not resolve to an authorized source record. Design source bindings only after one source/domain is selected. |
| **No approved predictive question or target semantics** | `target_key`, label, unit, currency, dimensions, and origin are caller input. The service can technically forecast a `revenue` target without establishing what that target represents. No finance/Operations/customer owner, source, KPI, forecast objective, or business success threshold is established by M17. |
| **Input readiness is technical, not business suitability** | Dataset eligibility checks calendar alignment, observation counts, missing/unobserved panel periods, and resource limits. It does not prove complete population, minimum useful history, source freshness, stable definitions, representative history, seasonality, concept drift, or policy approval. Phase 2 needs an owner-approved readiness contract and explicit abstention states; do not turn existing candidate status into business approval. |
| **No silent transformation guarantees beyond the current contract** | The current engine does not add an ingestion/transformation pipeline; it constructs an explicit dense timeline and reports absent periods as missing/unobserved. Keep that behavior. Any future calendar mapping, aggregation, frequency conversion, imputation, winsorization, normalization, currency treatment, or exclusion must be separately specified, versioned, visible, and tested—not silently introduced in an adapter or model. |
| **Limited method coverage** | The three baselines cannot model many trend, multiple-seasonality, holiday/calendar, exogenous-driver, intermittent-demand, regime-change, or probabilistic use cases. That is not evidence that a statistical library is required. Benchmark an approved question against these baselines first; if a baseline fails, document the gap and select at most one method family. |
| **Holdout reuse can be repeated through copied data** | The one-time holdout invariant is scoped to a dataset-version ID. The same series may be resubmitted under another dataset key/version and evaluated over the same dates, so the current uniqueness rule does not prevent repeated exposure while tuning. Before scores count as independent evidence, govern reuse at source, time-window, and content level across dataset versions. The proposed, unimplemented design is an owner-approved, append-only exposure ledger keyed to authorized source lineage plus target/dimensions/frequency and holdout origin/window/horizon, with privacy-preserving fingerprints of canonical exact observations (including per-period leaves to flag overlap) so copied or overlapping holdouts cannot silently be treated as fresh. A consumed/exposed window should be blocked or explicitly marked reused; evaluation must use a new non-overlapping window or a separately governed holdout. The ledger/fingerprints do not prove source authority. Owners must approve canonicalization, overlap policy, access, key lifecycle, and retention. No clone-content regression test was identified in the reviewed M17 tests. |
| **Intervals are empirical, not calibrated guarantees** | Intervals use a per-series nearest-rank quantile of validation absolute errors. The implementation explicitly reports `empirical_non_guaranteed` and `not_established_for_time_series_dependence`; it does not prove nominal coverage, horizon-specific coverage, or probability. Do not present these intervals as confidence or prediction guarantees. Decide whether they remain hidden/disabled until independently calibrated for the selected use case. |
| **No drift/ongoing monitoring or forecast outcome lifecycle** | M17 stores a forecast and evaluation snapshot but does not link future observed outcomes to forecast periods or provide a governed rolling calibration/drift process. An observed outcome, later actual, accuracy evaluation, and new forecast must remain separate versioned evidence. Do not silently rewrite historical errors or claim a model stays accurate. |
| **No forecast retention/legal-hold policy** | Dataset snapshots contain submitted series, and evaluation/run snapshots contain predictions and actuals. M17 has no data-retention, deletion, legal-hold, or purge workflow. Append-only history and downgrade refusal are not a retention schedule. Owner/security/privacy approval is required before real or sensitive data is retained. |
| **Large module concentration** | M17’s current service is about 2,275 lines and its calculation module about 1,139 lines; routes/contracts/models are also substantial. This is manageable for its bounded prototype but raises change-review and regression risk if many model families or domain adapters are added. Prefer a small, measured extraction of domain-specific concerns only when the first approved vertical slice needs it; do not refactor the entire engine as a separate Phase 2 goal. |
| **Unkeyed hashes are integrity markers only** | M17 documents SHA-256 hashes as integrity references, not encryption or protection from privileged database operators. Hashes do not protect confidentiality or authenticate evidence. Preserve the existing warning and review storage/encryption/retention under the selected data classification. |

### Proposed holdout reuse governance (design only; not implemented)

Any later P2-03 implementation should replace dataset-version-only consumption with a governed holdout identity and exposure record:

1. **Bind the test window to trusted scope.** Resolve Company and source lineage server-side; define the holdout scope using the authorized source/record versions, target, dimensions, frequency/calendar, fixed forecast origin, exact test-period range, horizon, and evaluation protocol. A caller-provided source ID or timestamp is not sufficient identity.
2. **Fingerprint content and overlap without storing another raw copy.** Use a documented canonical encoding of the exact accepted period/dimension/value-or-missing-reason entries and source-version references. Store a keyed, versioned HMAC for the complete holdout and per-period/dimension leaves so exact clones under new dataset IDs and overlapping windows can be detected. Any numeric normalization must be an explicit versioned choice; do not normalize or transform implicitly. The HMAC is a duplicate-detection token, not encryption, authorization, or proof of source authority.
3. **Record exposure append-only and fail closed on reuse.** An immutable, Company-scoped exposure ledger should bind scope/content fingerprints to the evaluation ID, protocol/model versions, actor, timestamp, and whether holdout results/actuals were disclosed. A uniqueness/serialization rule should prevent concurrent requests from consuming the same governed window twice. A repeated or overlapping window should be blocked for independent scoring or returned explicitly as already exposed/reused—not counted as a new independent holdout. Because current evaluation responses expose holdout results, treat a completed response as exposure.
4. **Require untouched evidence for independent evaluation.** Use a later, non-overlapping chronological window or a separately governed external holdout. If neither is available, label subsequent comparisons exploratory and do not claim independent holdout evidence. Keep validation/tuning windows distinct from the final holdout.
5. **Obtain owner/security/privacy decisions first.** Approve source identity, overlap policy (including corrected records and cross-source duplicate treatment), canonicalization, HMAC key custody/version/rotation, ledger access and retention, and what happens when the same period appears with changed content. Add tests for identical content under new dataset/version IDs, partially overlapping windows, changed values, corrected source versions, concurrent evaluation attempts, and Company isolation.

This is a design recommendation only. No ledger, fingerprint, database migration, API change, test, or other holdout-control implementation is part of P2-00.

The M17 model/protocol hashes and replay bind a calculation to the application’s engine/version and stored evidence. Replay is useful for reproducibility, not an independent source audit, independent model validation, business approval, or proof of forecast accuracy.

## 6. Data lineage and proposed architecture boundary

A future predictive path should use an explicitly authorized source domain, not ask an API client to submit arbitrary observed values and self-assert their provenance:

```text
One Company-selected, authorized domain source
        |
        v
Domain-owned source contract + access/readiness checks
        |  (authority, rights, freshness, completeness, correction, retention)
        v
Typed, immutable, lineage-bound dataset snapshot
        |  (no implicit aggregation, imputation, normalization, or frequency change)
        v
Existing M17 baseline / chronological evaluation / one approved model extension
        |
        v
Immutable evaluation and forecast snapshots + replay + limitations/abstention
        |
        v
Optional, separate human review under an approved role/policy
```

This is a target boundary, not an approved implementation. Prefer one in-process adapter in the domain that owns the facts, with M17 consuming its validated snapshot, rather than a new ingestion framework or a second forecasting service. Universal Data may be the source for a selected non-financial domain only if its source/record contracts and permission checks fit that use. M14/M16 require independent finance-owner/source approval and cannot be treated as generally approved forecast history. M5/Operations/BI outputs must retain their present semantics and permissions.

M17’s existing JSON snapshot and 0026 tables may be sufficient for an initial non-production experiment after input construction is server-owned. If the approved requirement needs durable direct source binding, explicit policy/readiness state, outcome links, or governed retention that cannot be represented safely by the existing snapshot contract, a new additive migration may be needed. It must be specified against the selected domain and preserve same-Tenant/Company FK scope, forced RLS, least privilege, append-only history where appropriate, and purge/downgrade protection. No migration is selected or proposed for implementation now; do not modify 0026 or any earlier migration.

## 13. Testing and verification plan for any future approved slice

1. **Contracts and pure calculation:** strict input types; exact decimal-text preservation; calendar/frequency alignment; deterministic known-vector forecasts; duplicate period/dimension rejection; explicit missing/zero/negative values; undefined metrics; size/budget caps; output hash and replay.
2. **Temporal leakage:** chronological train/validation/test boundaries; fixed-origin future forecasts; verify that changing values after a forecast origin does not alter earlier predictions; no holdout fitting/calibration; test clone/overlap holdout reuse across newly submitted dataset versions.
3. **Data readiness and lineage:** source ID/version/record references resolve only within the authenticated Company; stale/revoked/incomplete/unauthorized/corrected/conflicting source evidence blocks or produces the owner-approved explicit partial state; no transformations beyond the reviewed specification; exact lineage survives replay.
4. **Comparison and statistical validation:** compare against the three current M17 baselines on identical scoring data and horizons; test representative synthetic edge cases (trend, seasonality, intermittent history, missing periods, zeros, outliers) without treating them as customer evidence; evaluate on an independently governed chronological holdout. No accuracy claim follows from passing this software suite.
5. **PostgreSQL/API security:** disposable PostgreSQL 18.7 integration database with separate runtime/migrator/admin roles; authorized/unauthorized users, two tenants/companies, source permissions, forced RLS, grants, append-only triggers, migration/model parity, concurrent writes/versioning, body/resource limits, and downgrade/retention guards. Use the current Alembic/test workflow, not static SQL rendering alone.
6. **Replay and upgrades:** replay exact saved source/data/model/protocol/runtime identities; document unsupported old engine versions; verify tamper detection and status behavior across version changes. Reproducibility must include dependency/runtime identity if any library is added.
7. **Dependency and on-prem review (if any package is selected):** pin artifacts; inspect licenses/notices and full transitive dependency graph; SBOM/security-advisory scan; test supported Python versions and deployment architectures; demonstrate offline wheelhouse build/install, no outbound inference/runtime downloads, bounded resource use, and numeric/replay consistency.
8. **P2-00/Entry Gates verification:** no application tests or Alembic CLI validation were run for this documentation-only package. The original P2-00 creation checks are historical. For this Entry Gates change, documentation checks on the six `docs/phase2/` files verified 102 repository-relative links, 18 Markdown tables with 135 body rows, approved milestone order, no trailing whitespace, and final newlines; `git diff --cached --check` passed. Exact Git status and changed-path scope were checked separately.
