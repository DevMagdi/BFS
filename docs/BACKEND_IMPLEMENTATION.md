# Backend implementation baseline: Milestones 2–8, 10–16, Phases 1–3, and experimental Core Financials

## Implemented components

The code targets Python 3.11–3.13 under the current package metadata and uses a modular-monolith structure with FastAPI, SQLAlchemy 2, Alembic, psycopg 3, and PostgreSQL. PostgreSQL is required; SQLite does not exercise the RLS guarantees and is not an integration-test substitute. Compose and CI are pinned to PostgreSQL 18.7 for integration validation, including Core Financials.

Each tenant has one primary company. A unique company `tenant_id` enforces one company per tenant; the deferred composite tenant-to-primary-company foreign key ensures the primary company belongs to that tenant. Company creation and the initial active owner membership are committed in the same database transaction as the tenant and idempotency record. An identical retry with the same user/key and request returns the original tenant; reusing that key with changed request data is rejected.

Memberships are soft-revoked rather than physically deleted. The application serializes owner changes using a tenant lock and rechecks authorization under that lock. A deferred PostgreSQL constraint trigger also rejects a commit that would leave an active tenant with no active owner.

### Milestone 3 company-context rules

- Business units and departments have active/inactive status. A department may have one optional business unit. Units cannot be deactivated while active departments remain; departments cannot be deactivated while active or on-leave employees remain. The API's `DELETE` operations are soft deactivations, not physical deletes.
- An `Employee` is a business record, separate from `UserAccount`; employee records do not require product logins. The implemented fields are an employee code, name, job title, optional department, employment status/dates and standard weekly hours. No compensation, payroll, manager hierarchy or employee-to-user link is implemented.
- Skills have a tenant-scoped catalog and employee-skill records. Proficiency is an integer from 1 through 5 (`beginner`, `working`, `proficient`, `advanced`, `expert`). Catalog entries and employee-skill records are soft-deactivated; historical associations are retained.
- Weekly capacity is recorded for Monday–Sunday weeks, with each record anchored by a Monday date. `confirmed` and `estimated` records require scheduled, non-project and unavailable hours; the reported known hours are their difference. `unknown` requires all hour fields to be absent and produces no available-hours value. Missing and unknown capacity are never inferred from an employee's standard-weekly-hours field. Corrections append a monotonically versioned record; the runtime role cannot update or delete capacity history.
- Project transitions are `draft` → `planned`/`cancelled`, `planned` → `active`/`on_hold`/`cancelled`, `active` → `on_hold`/`completed`/`cancelled`, and `on_hold` → `active`/`completed`/`cancelled`; completed/cancelled projects are terminal and immutable. Completion requires an actual end date, and an actual end date is only valid for a completed project. Resource assignments transition `proposed` → `committed`/`cancelled` and `committed` → `completed`/`cancelled`; completed/cancelled assignments are immutable. Only planned/active projects and active employees may receive committed assignments. A project cannot close while proposed or committed assignments remain. Manager-adjustment capacity requires a reason and manager-adjustment assignment creation requires a note. Assignment changes and cancellations are preserved as append-only audit events and exposed through a paginated history endpoint.
- The `/company-context` summary reports stored facts and coverage, not a recommendation or feasibility score. It returns counts, bounded/truncated lists, weekly capacity coverage and assignment facts, and explicit indicators for missing, unknown or estimated information. It does not treat planned assignment hours as proof that capacity is available.

Public registration is disabled: `POST /api/v1/auth/register` is not mounted or listed in OpenAPI, and migration `0014_disable_public_signup` removes effective table- and column-level `INSERT` on `public.users` from `PUBLIC` and `bf_runtime`. Migration `0015_limit_runtime_users_update` revokes all table- and column-level `UPDATE` on `public.users` from those principals; `bf_runtime` receives no account-write privilege. Because the application uses one shared database role and `users` has no RLS, there is no safe database-enforced row scope for login-time password rehash. Login verifies existing Argon2id hashes but does not rewrite them; legacy hashes remain usable at their stored parameters. Both migrations inspect actual `pg_roles` attributes and fail closed unless `bf_runtime` is `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOINHERIT`, and has no role memberships. They also fail closed on runtime ownership or delegated user-table grants; bootstrap independently checks the same role and complete effective privilege policy. Existing accounts are not changed. Downgrading either revision preserves the user-table INSERT/UPDATE revocations, so older application code that depends on registration, user-row updates, or automatic password rehash may fail closed; a schema downgrade is not a privilege rollback. Login, refresh, logout, and `/auth/me` remain available. Passwords use Argon2id (the initial configured parameters are 19 MiB memory, two iterations, one lane). Access tokens are HS256 JWTs with issuer, audience, token-use, user, session, and token identifiers. Requests validate both the token and the corresponding unrevoked database session. Refresh credentials are random opaque values; only SHA-256 digests are stored. Refresh rotates the token, detects reuse, and revokes the session and its refresh-token family. Logout accepts either a valid access token or the opaque refresh credential, allowing revocation when the access JWT has expired; refresh and logout serialize through the session lock. Logout failures are not reported as success, and the browser warns if the server cannot confirm revocation. Disabled accounts cannot log in, refresh, or continue using an existing access session.

Login throttling uses atomic PostgreSQL upserts for HMAC-hashed email and source-IP buckets. Defaults are five failed attempts per email bucket and twenty per source-IP bucket in a fifteen-minute lockout window; all are configurable. Raw passwords and bearer/refresh tokens are not written to audit metadata or application error logs. Validation and authentication errors return a bounded safe error shape with a request ID.

The API returns access and refresh tokens in JSON, not cookies. The M10 browser client stores them in `sessionStorage` and coalesces a single in-flight refresh across normal API requests and blob/download requests in the same tab. Each retried request is attempted at most once; refresh failures do not loop, and invalid refresh credentials clear that tab's auth state once. The API's one-time refresh rotation and replay detection remain authoritative.

Cross-tab refresh coordination is not implemented. `sessionStorage` is scoped to a tab, so tabs can hold separate or initially copied refresh-token values; the browser client cannot reliably share the newly rotated value across them. If two tabs submit the same one-time refresh token, backend replay protection may revoke the session. Do not treat simultaneous multi-tab use as supported. **MVP recommendation:** keep multi-tab use out of the MVP support promise for this bearer-token design. If simultaneous multi-tab use is a launch requirement, resolve it first with a reviewed shared server-managed cookie/session and CSRF protections; do not move refresh tokens into persistent `localStorage`, weaken replay protection, or add ad hoc cross-tab token coordination.

### Local account and tenant onboarding status

For this remediation, public self-service registration is disabled, and an authorized deployment operator provisions the first owner with the one-time `businessflow-admin bootstrap-owner` command. It requires an interactive terminal, a `BOOTSTRAP_DATABASE_URL` that authenticates directly as the non-superuser `bf_migrator` role, and an empty installation. It obtains the initial password through hidden terminal input (never a command-line argument), hashes it, creates the owner and first tenant/company in one transaction, serializes concurrent runs, and refuses to run again once any account exists. It emits no password, token, or database URL and sends no email. See [`../scripts/README.md`](../scripts/README.md).

Migration `0014` revokes the runtime role's ability to insert new user rows; `0015` revokes all runtime `UPDATE` on user rows. Downgrading either revision keeps those revocations in place. Older application versions that expect runtime account creation, profile/status updates, or login-time password rehash can therefore fail closed after a schema downgrade; do not treat Alembic downgrade as restoration of the old privilege contract. The current login path verifies existing Argon2id hashes without rehashing them. These migrations do not update, delete, or deactivate accounts or memberships. The populated legacy-schema upgrade test verifies the existing active owner membership remains attached to its user and tenant. Legacy email ownership is not established by that migration. New tenant membership creation is temporarily unavailable and authorized member-role requests return `membership_invitation_unavailable`; no invitation or verification tokens are issued because no delivery provider or token policy has been approved. Only operator-provisioned first-owner onboarding is currently supported for a new installation. Broader onboarding requires an approved email-delivery provider and owner-approved invitation/verification security and token-lifetime policy. End-to-end invitation onboarding is not implemented. MFA and password recovery are also not implemented.

The service layer and API enforce this permission matrix:

| Role | Tenant read/update | Company read/update | Membership read/create/manage | Audit read | Company-context read/write | Decision read/submit/review | Finance read/write |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Owner | Yes / Yes | Yes / Yes | Yes / Temporarily unavailable / Yes | Yes | Yes / Yes | Yes / Yes / Yes | Yes / Yes |
| Admin | Yes / No | Yes / Yes | Yes / Temporarily unavailable / Member-only | Yes | Yes / Yes | Yes / Yes / Yes | Yes / Yes |
| Member | Yes / No | Yes / No | No | No | Yes / No | Yes / No / No | No / No |

For M7, owners and admins can submit decisions and review another active owner's/admin's decision; members have read-only access. Separation of duties is mandatory and enforced both in the service and database: a submitter cannot review the same version, and every version has at most one immutable review result. At least two eligible owner/admin principals are required. There is no self-approval exception. Decision permissions are scoped by active membership, tenant, company and intake; details and stale-evidence behavior are documented in [`M7_DECISION_APPROVAL.md`](M7_DECISION_APPROVAL.md).

Administrators may manage existing member-role memberships but cannot grant or change owner/admin privileges. New membership creation is temporarily disabled; matching an active account by email is not sufficient verification, and the endpoint returns `membership_invitation_unavailable`. Existing memberships and their access are preserved. A user cannot modify their own membership; the final active owner cannot be revoked or demoted.

### Milestone 4 staged imports

The import API is mounted under `/api/v1/tenants/{tenant_id}/imports` and is company-context scoped. It supports six dataset types: employees, skills, employee skills, weekly capacity, projects, and resource assignments. Upload accepts UTF-8 CSV (optional BOM) and XLSX only. The default limits are 25 MiB per upload, 10,000 nonblank data rows, and a 24-hour staging TTL; environment settings bound configurable limits.

Inspection reports worksheet/header/row metadata and dataset suggestions. Mapping is explicit: every source column must map to a supported field or be listed as ignored. Validation produces row-level safe issues and deterministic counts, identifies in-file and canonical duplicates, and never overwrites an existing canonical record. Preview is paginated. Confirmation requires the latest validation hash, explicit warning acknowledgement when warnings exist, and explicit partial-apply permission when invalid rows exist. The apply request revalidates the mapping, source rows, referenced company records, and duplicate state before using the existing canonical create services. Audit events are written for upload, mapping, validation, confirmation, expiry, cancellation, and application; row links preserve source-to-canonical traceability. Upload retries—including concurrent retries—with the same key, user, and file hash return the original import; a changed request conflicts. Applying an already-applied import returns its prior link count with `replayed: true`.

The XLSX parser uses `openpyxl` with defused XML and rejects formula cells, hidden worksheets, macro parts, external workbook links/relationships, unsafe ZIP paths, excessive archive entries, high compression ratios, and expanded-size/worksheet/column/row limits. The API does not evaluate uploaded formulas. Raw staged values are cleared on apply, cancellation, or expiry. Expired items are purged in bounded batches by the owner/admin `POST /api/v1/tenants/{tenant_id}/imports/purge-expired` endpoint; a deployment scheduler must call this endpoint (or a future maintenance worker) to enforce unattended expiry. The implementation does not define legal retention for audit metadata or backups.

### Milestone 5 deterministic metrics

The API exposes `GET /api/v1/tenants/{tenant_id}/metrics/catalog`, `POST /api/v1/tenants/{tenant_id}/metrics/runs`, and `GET /api/v1/tenants/{tenant_id}/metrics/runs/{run_id}`. Catalog version is `businessflow.metrics.v1`; calculation version is `businessflow.capacity-weekly.v1`. The catalog contains five non-financial definitions: `available_capacity_hours`, `recorded_committed_hours`, `capacity_minus_recorded_commitments_hours`, `recorded_assignment_overload`, and `recorded_skill_inventory_coverage`. The API and persisted result explicitly label the catalog `implementation_draft` and its use `observational_only_no_recommendation`; versioning does not imply owner/finance approval. A run starts on a Monday and covers 1–52 weeks.

The calculation is pure Python, deterministic, input-order independent, and uses `Decimal` hours serialized at two decimal places. It snapshots current tenant/company-scoped canonical facts and available retained M4 source-row links, calculates the result, and persists both JSON-compatible snapshots plus canonical SHA-256 hashes in one repeatable-read transaction. The input hash covers the canonical fact/lineage snapshot and period; the result hash covers the values, metric catalog and calculation versions, per-metric versions, and a snapshot of the metric definitions and formulas. Each run records the requester, period, reliability status and audit event. The snapshot retains import ID/status, dataset, mapping version, file and row hashes, source-row identity/location, and the canonical fingerprint captured at import; it does not copy staged cell payloads. A saved input snapshot can be deserialized and replayed against the same calculation implementation/version and checked against the stored result hash.

Metric interpretation and limits:

- Weekly available capacity is `scheduled_hours - non_project_hours - unavailable_hours`, using the latest version for each active employee/week. Confirmed and estimated values are separate. Missing, explicitly unknown, invalid or conflicting values remain unknown; standard weekly hours are never a fallback. A complete company subtotal is emitted only when capacity is known for every currently active employee.
- Only committed assignments are compared with capacity; proposed hours are separate. Each assignment contributes its full planned weekly value to every Monday–Sunday week intersecting its inclusive dates; no daily proration occurs. No assignment rows means not recorded, not zero, and assignment completeness is not attested.
- Employee overload comparisons are emitted only when the employee has known capacity. Confirmed and estimated overloads are distinguished; missing, unknown or invalid capacity is reported as unresolved. Capacity minus recorded commitments is null unless all active-employee capacity is known and at least one active employee commitment is recorded. Even when available, it is an arithmetic observation—not proof of free capacity, actual work, timesheets or utilization.
- Skill output counts current active employee-skill records by active skill and proficiency (1–5). It is recorded inventory only; project-required skills, matching, practical competency and delivery capability are unsupported.
- Current active employee status is applied to every requested week because M3 has no historical employment-status model. Run-level reliability describes weekly-capacity coverage only; assignment and skill states are reported separately.

Calculation inputs are bounded to 52 weeks, 1,000 active employees, 10,000 overlapping assignments, 2,000 active skills, 20,000 active employee-skill records and 50,000 retained lineage references. Oversized inputs are rejected rather than silently truncated. The service enforces existing `company_context:read` membership authorization; saved runs are visible only within the authorized tenant/company. The database enforces forced RLS and runtime select/insert-only access. The local verification described below covers replay, source lineage, authorization, tenant isolation and append-only grants using PostgreSQL.

### PostgreSQL roles and RLS

The local initialization script creates separate roles:

- `bf_migrator` owns the application databases/schema objects and is the only role permitted to run the Alembic migration;
- `bf_runtime` is the API's non-superuser, non-owner, non-`BYPASSRLS` role, with no schema `CREATE` privilege and only the table privileges required by the application; and
- the bootstrap/admin role is used only to initialize local PostgreSQL and, in tests, inspect/reset the dedicated test database.

The foundation migration rejects a missing or superuser/`BYPASSRLS` `bf_runtime`, membership in `bf_migrator`, database ownership, and `public` schema `CREATE`. Revisions 0014/0015 additionally inspect the live role and require `NOSUPERUSER`, `NOBYPASSRLS`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOINHERIT`, and no role memberships; they also reject ownership of `public.users` or the application database and database/schema `CREATE`. Those revisions revoke table- and column-level user INSERT/UPDATE grants only from `PUBLIC` and `bf_runtime`; they fail closed on extra role membership or delegated runtime grants rather than revoking privileges from unrelated roles or cascading. The resulting runtime ACL denies all user INSERT and UPDATE. Both downgrade paths retain these revocations; they do not restore the older privilege contract. The migrations enable and force RLS on `tenants`, `companies`, `tenant_memberships`, `tenant_onboarding_requests`, `audit_events`, all eight Milestone 3 tables, all three Milestone 4 import tables, M5 `metric_runs`, M6 `project_intakes`, `project_intake_versions`, and `capacity_assessments`, the three M7 decision/approval tables, M8 `project_financial_input_cases`, `project_financial_input_versions`, and `financial_assessments`, all five M10 position-review tables, M13 `metric_insight_runs`, M14 `finance_source_mappings`, `finance_source_intakes`, and `finance_source_row_evidence`, M15 `financial_calculation_runs`, the six Core Financials policy, mapping, import, record, run, and run-evidence tables, and Phase 1's `manual_customer_commitments`, `manual_customer_commitment_events`, and `manual_customer_commitment_evidence`, plus Phase 3's `business_semantic_entities`, `business_semantic_mapping_versions`, and `business_semantic_relationship_versions`. Each tenant-owned table has a tenant-context policy; M6–M10, M12–M15, Phase 1, Phase 3 semantic tables, and Core Financials company-scoped records additionally require verified company context. The global M12 and M14 contract catalogs are read-only to `bf_runtime` and contain no tenant data. Request code sets verified user and membership-authorized tenant/company context with transaction-local PostgreSQL settings. Missing context returns no tenant rows and rejects tenant writes. Context is discarded with the transaction, including when a pooled connection is reused.

The M3 runtime role can select, insert and update the company-context tables, but cannot physically delete them. `employee_weekly_capacity` is append-only for the runtime role (select/insert only) and also has a database trigger rejecting update/delete. The M4 runtime role can select/insert/update staged imports and rows but cannot delete them; it can only select/insert canonical trace links. The M5 runtime role can select/insert `metric_runs`, with no update/delete/truncate privilege. M6 versions and assessments are select/insert only for `bf_runtime` and protected from update/delete by database triggers; intake updates are limited to the `project_code`, `current_version`, and `updated_at` columns, with a trigger requiring exactly one version advance. M7 versions and approvals are also select/insert only and guarded against update/delete/truncate; only the case's current-version pointer can advance, and database guards verify the new immutable version and approval bind the exact current evidence and satisfy the separation-of-duties policy. M8 input versions and financial assessments are select/insert only for the runtime role and protected by append-only guards; the financial-input case pointer advances only with a new version. M13 `metric_insight_runs` is select/insert only and protected by append-only guards. M14 mappings, intakes, and row evidence are select/insert only and protected by append-only guards; the global finance contract is read-only and append-only. M15 adds the same select/insert-only and append-only protections to `financial_calculation_runs`; the commitment columns on M14 row evidence are covered by its existing read/insert-only and append-only boundary. Phase 1 grants `bf_runtime` select/insert/update only on the current commitment row, select/insert on event and evidence history, and no delete/truncate; database triggers enforce lifecycle transitions, a matching event per revision, acceptance criteria, evidence limits, and append-only event/file behavior. Phase 3 semantic entities and mapping/relationship versions are select/insert only and protected by append-only triggers; all three tables use forced tenant/company RLS and same-scope composite references. The manual source is registered through this guided flow and is excluded from M4 imports and the six-dataset M12 coverage grid. Soft deactivation/cancellation, versioned capacity, decision, financial, insight, finance-source, calculation and commitment evidence, and purgeable staging payloads preserve the current facts and history.

The global `users` and authentication-state tables are not tenant-RLS tables: authentication must locate a global account before tenant membership is known. Their API access is constrained by service queries and the user/session identity checks. Tenant-owned records are separately scoped at the service/API boundary and by PostgreSQL RLS. Unscoped authentication audit events can be inserted only under the narrow policies in the migration; tenant audit reads remain tenant-scoped. Audit rows are append-only for the runtime role through grants and database triggers.

## Local development

### Recommended: Docker Compose

1. Install Docker Engine and the Compose plugin. Copy the safe example and replace every placeholder with an independent URL-safe random value; never use these examples as production secrets.

   ```sh
   cp .env.example .env
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

   Generate distinct values for the PostgreSQL initialization-superuser password (`BF_BOOTSTRAP_PASSWORD`), `BF_MIGRATOR_PASSWORD`, `BF_RUNTIME_PASSWORD`, and `APP_SECRET_KEY`. `BF_BOOTSTRAP_PASSWORD` is not the BusinessFlow owner's password; the owner password is entered through hidden terminal prompts to `businessflow-admin bootstrap-owner` as documented in [`../scripts/README.md`](../scripts/README.md).

2. Initialize PostgreSQL, apply migrations as `bf_migrator`, start the API as `bf_runtime`, and check readiness:

   ```sh
   docker compose --profile tools run --build --rm migrate
   docker compose up --build --detach api
   curl --fail http://localhost:8000/health/ready
   ```

   The API listens on port 8000 by default; set `API_PORT` to change the host port. Migrations are an explicit step and are not run automatically by the API container.

3. The full PostgreSQL integration suite is destructive: its fixture downgrades the configured test database to Alembic `base` and rebuilds it. Prefer the CI workflow, which provisions a fresh per-job PostgreSQL service. **Do not run `docker compose --profile test run --build --rm tests` against the normal Compose stack.** That test service connects to the same PostgreSQL service backed by the persistent `postgres-data` volume; using a separate database name such as `businessflow_test` does not make the server or its data disposable. Run the suite locally only against a newly provisioned, isolated disposable PostgreSQL instance after verifying the exact server, database, roles, and absence of persistent/shared data. Never point any `TEST_*_DATABASE_URL` at development, staging, production, an existing developer database, or data that must be kept. Tests require PostgreSQL runtime, migration, and separate admin URLs; the runtime and migration URLs must use `bf_runtime` and `bf_migrator` respectively.

4. Stop services with `docker compose down`. **`docker compose down -v` deletes the local PostgreSQL volume and all data**; use it only when intentionally resetting the environment. Database-init scripts run only on an empty volume; changing `.env` passwords does not change roles in an existing volume. See [`scripts/README.md`](../scripts/README.md).

### Python tools

Create an environment and install the project plus development tools:

```sh
python3.11 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
```

For a host-run API or test suite, provision PostgreSQL and the separate roles using the same ownership/grant model as `scripts/db-init/010-create-roles.sh`, export `DATABASE_URL` for the runtime role and `MIGRATION_DATABASE_URL` for `bf_migrator`, then run:

```sh
.venv/bin/alembic upgrade head
.venv/bin/uvicorn businessflow.main:app --host 0.0.0.0 --port 8000
```

For tests, also export `TEST_DATABASE_URL`, `TEST_MIGRATION_DATABASE_URL`, and `TEST_ADMIN_DATABASE_URL` for the same dedicated test database, with `bf_runtime`, `bf_migrator`, and a separate test-admin role. All PostgreSQL URLs must use the `postgresql+psycopg` driver. Then run:

```sh
.venv/bin/pytest -q
.venv/bin/ruff format --check src migrations tests
.venv/bin/ruff check src migrations tests
.venv/bin/mypy src/businessflow
```

`APP_SECRET_KEY` must be a non-placeholder value of at least 32 characters; use a separately generated secret of at least 48 URL-safe characters. Production configuration rejects common `dev-`, `test-`, and `ci-` prefixes. Avoid sharing `.env`, database URLs, access tokens, refresh tokens, or test-admin credentials.

The GitHub Actions workflow at `.github/workflows/backend.yml` provisions isolated PostgreSQL 18.7 and asserts the exact server version before running formatting, lint, mypy, Alembic upgrade/drift checks, and the full integration suite. Its fixed credentials are disposable test-only values, not application secrets.

## Known limits, reuse review and deployment notes

This is a bounded backend/workflow implementation, not a claim of production readiness. Narrow static browser flows exist for synthetic M10, capacity decisions (PR #26), and default-disabled Core Financials; this branch adds a Company Data Foundation page spanning M4/M12 evidence, Phase 1 manual commitments, and Phase 2 Universal Data, plus a backend-only Phase 3 Business Semantic API (no dedicated UI). These are not a unified BI workspace. There is no general-purpose frontend, CORS policy, email service, account recovery, MFA, secret-rotation mechanism, or operational monitoring/backup design here. M10 remains synthetic-only and is not a general dashboard or customer-data path. M5 is limited to the non-financial capacity, recorded-assignment and skill-inventory observations above. M6 adds versioned proposed-project intake and a human capacity-only comparison with explicit weekly team-hour demand; its sole hypothetical scenario is a demand schedule for that same comparison, not a multi-option decision engine. Job-role catalogs, non-employee resources, HR/payroll, compensation, canonical time-entry/cost/revenue/accounting records, contracts, automatic identity resolution or automatic cross-source customer/supplier merges (Phase 3 permits only explicit human-reviewed Company semantic links over source-scoped Universal Data references), company-wide financial fact models, approved financial calculations/policies, actual-work/utilization data, project skill requirements, a general KPI framework, non-project decision subjects, option recommendations, and broad business/commercial feasibility decisions remain out of scope. M8 accepts project-scoped sourced observations only; it does not canonicalize or calculate them. General M4 imports remain limited to the six CSV/XLSX workforce/project datasets; M10 adds five pinned synthetic CSV templates only. M12's source-registration and evidence registry remains bound to M4. Phase 2 Universal Data adds a separate CSV/XLSX staging/mapping/validation/promotion workflow and one optional bounded local-directory reader; it has no remote connector, sync worker, or background scheduler. Records remain source-scoped and do not automatically merge or become Core Financials facts. If deployed behind a reverse proxy, configure trusted proxy handling so login throttling receives the intended client IP; do not trust arbitrary forwarded headers. TLS termination, production secret management, backup/recovery, capacity tuning, and broader threat-model review are deployment gates outside this code delivery.

M7 adds project-stage decision versions and their audit/history; M8 adds sourced project-level financial observation snapshots and an assessment that stays `incomplete` without approved policy. Neither implements company-wide finance, financial calculations, broad commercial acceptance/rejection, a recommended option, hiring/outsourcing, resource allocation, autonomous decisions, external actions, or outcome tracking. Narrow UI workflows exist separately and do not expand M7/M8 business scope. M6 completeness/currentness remains an explicit human assumption. M7 detects changes represented by newer M6 assessments and newer persisted M5 metric runs; it cannot prove an upstream source is current if no refreshed evidence run is recorded. Approval is limited to owner/admin review of the exact current capacity-stage decision version with matching hashes; no approval carries forward to a superseding version. Local M7 verification used embedded PostgreSQL 16.2, while current configured CI uses PostgreSQL 18.7; these environments are reported separately.
