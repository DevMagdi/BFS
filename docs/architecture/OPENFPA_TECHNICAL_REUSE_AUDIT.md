- **Decision status:** Technical audit and adoption recommendation only. This document does not approve implementation, accounting policy, a customer integration, or a dependency.
- **Audit date:** 2026-11-21 (UTC).
- **BFS baseline reviewed:** `5ec35f04ce317a613ac4b421d0c013ec004aa487` (`origin/main` at audit time).
- **OpenFPA snapshot reviewed:** [`ddac4e90edc7b93392d94f33c8f579100fe3f7e7`](https://github.com/JeffBrines/openfpa/tree/ddac4e90edc7b93392d94f33c8f579100fe3f7e7), including source, tests, dependency metadata, CI, examples, and license.

- **Test execution boundary:** OpenFPA tests were inspected, not run in this workspace. Its development dependencies are not installed here; no dependency was installed for this audit. BFS validation for this branch is documentation consistency only.

## Decision in brief

**Do not import the OpenFPA package into BFS. Do not copy its float/pandas financial kernel into the BFS calculation path.** The MIT license permits reuse with the required notice, but the package is a local, file-oriented toolbelt with floating-point model values; it has no BFS tenant/company security, PostgreSQL persistence, RLS, API contracts, or authenticated policy authority. Its source is useful for identifying worked financial mechanics, fixture/reconciliation checks, forecast evaluation concepts, and generated-workbook parity tests. Those patterns must be translated into BFS-owned, Decimal-based, versioned contracts and services.

There is no OpenFPA component recommended for **REUSE DIRECTLY** in BFS. Specific reusable *patterns* are classified **ADAPT** or **DESIGN INSPIRATION ONLY** below. BFS already has meaningful capabilities in M5, M8, M10, M11, and M12; extending those is preferable to adding parallel registries, calculation kernels, or source-row stores.

### Classification matrix

| Classification | Decision for BFS |
|---|---|
| **REUSE DIRECTLY** | **None.** MIT permits direct copying with notice, but no reviewed OpenFPA module is a drop-in fit for BFS tenant/company scope, PostgreSQL/RLS, Decimal contracts, policy approval, or APIs. |

| **DEFER** | Financial outputs, 13-week forecasting, model promotion, Excel calculation workbooks, broad live connectors, and AI/agent retrieval until required source evidence, domain owners, policy, security, and user requirements exist. |

## 2. OpenFPA repository, dependencies, license, and test posture

At reviewed commit `ddac4e90edc7b93392d94f33c8f579100fe3f7e7`, OpenFPA is an MIT-licensed Python package (`[LICENSE](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/LICENSE)`, `[pyproject.toml](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/pyproject.toml)`). Its declared runtime dependencies are `pandas>=2.0`, `pydantic>=2.5`, `pyyaml>=6.0`, and `openpyxl>=3.1`; `formulas>=1.2` is dev-only for workbook verification. BFS already declares `openpyxl` and uses Pydantic, but does not declare pandas or PyYAML; it has its own Decimal and ISO-4217 implementation. Do not add any of these dependencies merely to reuse OpenFPA.

MIT is permissive and allows copying/adaptation/distribution, subject to retaining the copyright and permission notice in copies or substantial portions; it gives no warranty. That legal permission is not a technical recommendation. If a later approved implementation copies any substantial code, retain the MIT notice and record the exact source revision and files. This audit recommends no direct code copy.

OpenFPA's checked-in CI ([`.github/workflows/ci.yml`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/.github/workflows/ci.yml)) runs `pytest -q` under Python 3.11, 3.12, and 3.13. The tests are mainly unit tests against example/synthetic configuration and local CSV/XLSX fixtures; they do not exercise PostgreSQL, tenancy, RLS, BFS authorization, or a customer accounting policy. The OpenFPA suite was not executed in this sandbox, so no claim is made that it passed here.

### Public-company example is not an accuracy certification

OpenFPA includes a real-source example in [`examples/foxfactory/pull_edgar.py`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/examples/foxfactory/pull_edgar.py), [`examples/foxfactory/foxf_model.py`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/examples/foxfactory/foxf_model.py), and `examples/foxfactory/data/`. `pull_edgar.py` actually requests SEC XBRL/EDGAR public data (using `curl`, a descriptive User-Agent, hard-coded Fox CIK/tags and SEC filing dates) and writes a documented snapshot. The checked-in tests use the local source extracts, not a live SEC request. `test_foxf_reconciliation.py` explicitly describes Phase A as actual-driver reproduction—target-year drivers are inputs—so it checks arithmetic mechanics, not independent forecast accuracy. Its separate FY2025 holdout and public worked example are useful evidence of a reproducible research workflow, not proof that its model is accurate for BFS or any other company.

## 5. Cash forecasting

OpenFPA's direct weekly model is in [`cash13/schemas.py`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/pyfpa/cash13/schemas.py), [`cash13/flows.py`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/pyfpa/cash13/flows.py), [`cash13/forecast.py`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/pyfpa/cash13/forecast.py), and [`cash13/runway.py`](https://github.com/JeffBrines/openfpa/blob/ddac4e90edc7b93392d94f33c8f579100fe3f7e7/pyfpa/cash13/runway.py): `WeeklyFlow` has a nonnegative float magnitude, start/end week, and once/weekly/biweekly recurrence; `cash13_forecast` totals receipts less disbursements from opening cash; `runway_summary` returns trough and first negative week. Default is 13 weeks but schema permits 1–52. There is no probabilistic collection model or automatic facility draw.

`tests/test_cash13_flows.py`, `test_cash13_forecast.py`, and `test_cash13_runway.py` cover recurrence, bounds, a few trajectories, trough, and negative cash. They do not validate invoice/receipt schedules against customer data, due-date changes, bank balances, multiple currencies, taxes/payroll, credit facilities, data completeness, or forecast accuracy.

**Decision: DESIGN INSPIRATION ONLY and DEFER BFS implementation to M16** (estimated **4–7 engineer-weeks** for one approved direct 13-week forecast). BFS has no production financial source contracts or cash forecast today. Prerequisites: M14 finance data contracts for the chosen cash, invoice/receivable, payables and scheduled-payment sources; data owner; precise opening-cash and timing semantics; explicit assumptions about committed vs forecast flows; M11 Decimal/currency/trace contracts; owner-approved quality and freshness rules. M15 is required only for a chosen accrual-to-cash/tax/debt bridge; a direct schedule should not imply that indirect P&L cash arithmetic is receipt evidence.

Acceptance must include immutable as-of/period and input snapshots; item-level source IDs and due dates; visible unknown, stale, disputed and assumed flows; explicit currency boundaries; exact replay and independently provided bank/control reconciliation; separate scenario inputs; a user-reviewed output; and no inferred receipt probability or payment execution. A 13-week label alone does not make an estimate reliable.

Local token search can be a UI convenience only after permission-filtered retrieval is enforced in the backend. Any future AI explanation must satisfy Evidence Before Answers; no model, vector store, or autonomous correction is selected here.

## 10. Final OpenFPA adoption choices

1. **Worth adapting:** explicit mapping-versus-ignore records, fixture-first connector contracts and golden reconciliation checks, source-profile checklist, holdout/evaluation field checklist, and workbook parity-test concept. These are patterns, not imports.
2. **Keep BFS-owned:** source/ingestion/quality/freshness contracts; company finance fact model; Decimal calculations/formula catalog; reconciliation trace and independent expected-result verification; cash forecast snapshots; forecast scoring and human promotion; durable history/permissions/RLS; APIs; and any connector runtime.
3. **Defer:** P&L and financial calculations until finance-owner policy; direct cash forecast until source contracts; forecast scoring/champion workflow until suitable actual history and evaluation protocol; Excel until canonical outputs; agent context/AI until a named workflow and permission-aware retrieval/security plan; integrations until a source is approved.
4. **Reject:** whole-package import, treating the `float` examples as BFS financial arithmetic, or relying on YAML/strings to enforce BFS authority.
5. **No accuracy claim:** neither passing OpenFPA/BFS software tests nor workbook parity establishes GAAP/IFRS/accounting correctness, real-company model suitability, cash forecast accuracy, or production readiness.
