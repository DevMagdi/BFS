## Recommendation

Carry **weekly incoming operational work-request volume for one owner-selected workflow** forward as the first candidate for business-owner review. The candidate is deliberately narrower than “predict operations”: it forecasts the number of new, distinct work requests first received in one selected workflow during the next Monday-start week, to inform that workflow’s next-week staffing or capacity plan.

This is a **proposed use-case contract**, not a statement that BFS currently records work requests, demand arrivals, a staffing decision, or a validated time series. Phase 1 Operations provides generic source-scoped events and exact-label counts; it does not define the semantics of `event_type`, a request lifecycle, throughput, demand, workload, or capacity decisions. The repository contains no real operational history from which to verify the candidate. Therefore Gate A remains **PENDING**, and the candidate must not be called selected or approved.

## What the repository establishes

The Phase 1 Operations implementation added by commit `463207710c78e74d18a24862bda1b40d7da21069`, merged by PR #41 as `366649e36b9d6cb5eaab53a4050b588cee4efeb6`, provides a useful starting boundary:

- Events are scoped to an existing Company Universal Data source. A manual event is explicitly a `manual_assertion`; a linked event must reference an exact same-source `business_activity` or `operational_record` revision. These are structural lineage controls, not proof of business authority, truth, or authorization for forecasting.
- Corrections append a version with predecessor/hash evidence. New Operations analyses use the current event versions for one source and an explicit half-open time interval, save input/result snapshots, and replay those snapshots.
- The only accepted Phase 1 calculation is a bounded count of recorded events grouped by exact event/state labels. The accepted scope expressly excludes a forecast, target, KPI, throughput, productivity, or decision interpretation.
- Operations’ source checks stop new writes for disabled/revoked sources and stop new analyses for revoked sources. They do not establish predictive-purpose rights, completeness, or a forecast-output invalidation policy.

M17, introduced by commit `22bc58128af67d499a40fd7463352e5332a86db3`, supplies weekly/daily/monthly contracts, deterministic `naive_last_value`, `seasonal_naive`, and `moving_average` baselines, chronological evaluation, and immutable replayable evidence. It accepts caller-asserted or synthetic datasets; source IDs and hashes in those records are caller-supplied references, not authenticated source lineage. The M17 paths and activation boundary are documented in [`M17_BASELINE_FORECASTING.md`](../M17_BASELINE_FORECASTING.md). The prototype remains default-disabled and blocked in `APP_ENV=production`.

## Historical evidence, suitability, and missing evidence

The tracked repository has no customer or operational time-series dataset, no historical weekly request counts, and no evidence that any available history contains independent periods. The Operations tests use inline synthetic events over illustrative timestamps; the M19 fixture contains synthetic customer rows. Neither is real operational history. No live production database was queried.

Consequently, the following questions have no evidence-based answer yet:

- **Actual coverage and independent periods:** no real observation window, history length, sample size, or independent holdout is available to inspect.
- **Missing periods and zeros:** source coverage is not measured. An empty event query is not proof that demand was zero.
- **Revisions:** Operations supports append-only corrections, but a corrected current event may change its event time/type. The existing Operations analysis reads current versions; M17 is not linked to this correction history or to an as-of-origin source snapshot.
- **Seasonality:** no real series exists to test weekly, annual, holiday, or other seasonal patterns. Do not configure a seasonal period from a synthetic fixture or assume that an available seasonal-naive baseline is appropriate.
- **Consistent target measurement:** no owner-approved event semantics, unique-request identity, duplicate policy, cancellation/reopen treatment, source timezone, or complete-period indicator exists.
- **Impact of error and incumbent process:** no acceptable error/cost of over- or under-forecasting, current manual/rule-based planning method, archived incumbent forecast, or capacity decision outcome is documented.

## Why this is a plausible first candidate—and why it is not ready

If an Operations owner confirms that one source records first-received work requests consistently, weekly intake volume is narrower than a generic “operations forecast,” can be measured in count units, aligns with the existing Operations evidence path, and can reuse M17 rather than introduce a second engine. A one-week horizon also keeps the first decision bounded.

Those are **conditional suitability arguments**, not evidence that the source exists or the decision is valuable. Without an accountable Business Owner, a real authorized source, enough corrected/revision-aware history, and an agreed incumbent-process comparison, real-source/business use remains blocked. Synthetic engineering may proceed under the separate owner authorization, but must record blockers and must not invent a substitute target.
