## Current implementation assessment

The product is a Python/FastAPI modular monolith with PostgreSQL, tenant/company authorization, forced RLS, bounded source evidence, deterministic runs, and human project decisions. It is **not yet** the integrated company-wide intelligence platform. Beyond the bounded M4/M12/M13 slices, Phase 2 Universal Data provides mapped, validated, promoted, source-scoped canonical records, and Phase 3 provides reviewed semantic identities/relationships plus a separate backend-only Business Intelligence API. That BI API offers versioned metric definitions and Company configuration, readiness, deterministic analyses from existing Universal Data/M5/Core Financials/saved-analysis evidence, immutable snapshots, replay, and paginated evidence references. It does not add ingestion, automatic identity resolution, a unified workspace, broad domain models, approved financial policy, or AI retrieval. Finance remains separately scoped and policy-gated, and live remote connectors remain absent. PR #26 added a narrow capacity UI. The Company Data Foundation adds coverage and evidence review over existing M4/M12 data, not an external ingestion system. Phase 1 adds a separate, manually captured customer-delivery commitment workflow with Company-scoped source provenance, review states, file evidence, and append-only history; it is not a Core Financials or M4 import path.

The minimum direction is incremental: source entry appropriate to each Company (manual capture for no-system workflows, mapped files, then governed connectors), optional typed domain facts, deterministic and replayable analysis, permission-aware read/decision APIs, task-focused UI, and AI only as an evidence-grounded interface with abstention. Keep PostgreSQL and the modular monolith; do not replace systems of record or add generic infrastructure without demonstrated need. Phase 1 records manual assertions and reviewer process, not completeness, authority, underlying-event verification, or financial truth. Its PostgreSQL integration test requires real PostgreSQL; local validation is limited to database-independent checks until the repository's PostgreSQL CI job passes. Real-browser E2E has not been performed.

## Historical M9 assessment details

## Executive assessment

**BusinessFlow can evolve toward the proposed platform by extending its existing modular-monolith foundation; it is not currently a company-wide BI or Decision Platform.** The strongest assets are the tenant/company security boundary, PostgreSQL forced-RLS and privilege separation, narrowly staged imports, deterministic snapshot/replay patterns, and M6–M8's immutable, human-controlled evidence chains. The main gaps are domain coverage, data-source breadth, company-level analytical views, financial-data governance/calculations, and a decision lifecycle that can bind to subjects other than proposed projects.

No evidence justifies replacing the working backend, changing repository/package/routes/database object names, introducing microservices or a new database, or forcing every company into one organizational model. Current project feasibility documents are a prior product hypothesis, not proof of the proposed broader product direction.

## Seven final assessment answers

### 1. Can the current architecture support evolution into a company-wide BI & Decision Platform?

**Yes, as an incremental direction—not as a claim that the product is already there.** The modular monolith, PostgreSQL, explicit tenant/company scope, service-layer authorization, forced RLS, and immutable versioned evidence provide a sound base for carefully selected domain slices. The target should add domain-specific facts and analytics behind the current trust controls and only compose them for a real, defined company question. There is no demonstrated need to replace the architecture or distribute it into services.

This is an architectural feasibility judgment only. No customer validation, deployment-scale study, or broad BI workload test is established by this repository review.

#### Evidence Before Answers — current footing and target gap

**Evidence Before Answers — No evidence, no confident answer** is an approved product requirement. The implemented M2–M8 slices provide useful but bounded building blocks; they do not provide AI answers or permission-aware AI retrieval:

| Requirement | Current implemented M2–M8 evidence | Target requirement / gap |
|---|---|---|
| Evidence-grounded | M4 source-row links; M5 available lineage; M6–M8 scoped source/evidence references. Coverage is limited to workforce/project data and project financial observations. | Each material AI answer claim must link to relevant authorized company data and source records; no source-free generated business claims. |
| Traceable and verifiable | M5 deterministic calculations, input/result snapshots, hashes and replay; M6–M8 versioned snapshots and exact evidence binding. | Expose supporting source records and calculation inputs/versions/results to inspection; no hidden or model-invented calculations. |
| Transparent | Current workflows preserve bounded status, warning, blocker, assumption and incomplete states. | Make assumptions, limitations, uncertainty, freshness, and missing/conflicting evidence explicit in every relevant answer. |
| Permission-aware | Backend membership/permission checks, company scope, composite keys, and forced PostgreSQL RLS protect current APIs. | Authorize before retrieval and before response; the model is never an authorization boundary. AI retrieval is not implemented. |
| Honest about insufficient data | M6 business feasibility and M8 financial verdict remain `incomplete` under their current bounded policies. | Abstain from confident conclusions when evidence is incomplete, unreliable, unauthorized, or lacks an approved policy across any future domain. |
| Reproducible | M5 supports snapshot replay; M6–M8 bind versioned inputs, calculations/decisions, evidence, and hashes. | Preserve input, calculation, policy, and evidence versions for important assessments and decisions. AI-response reproduction/audit is not implemented. |

For any future AI feature, local/on-prem inference is a target deployment requirement, not a currently implemented capability. No LLM, inference runtime, provider, vector store, or AI feature is selected or implemented.

### 3. Is the product already company-wide in its data or analysis?

**No.** Some current APIs and M5 totals read across the one active Company’s workforce/project context, but that is not broad company-wide business intelligence. The implemented facts are strongly concentrated in employee capacity, projects, assignments, and a proposed project-intake workflow. Projects are one supported business domain, not the product boundary. There are no general finance, sales, procurement, customer, product/service, ledger, budget, invoice, payment, or actual-work domains in the canonical schema. M8 adds sourced project observations, not a company finance model.

The schema enforces one `Company` per `Tenant` through `uq_companies_one_per_tenant` and the deferred tenant-to-primary-company composite FK in migration `0001`. Thus the current `Company` is a useful scope boundary, but the database does not support a multi-company group or consolidation view. A company-wide target does not require removing that constraint for its first slice.

### 5. What should the target architecture be?

Keep a modular monolith and PostgreSQL. Retain the security/evidence kernel and add optional domain-owned facts and analytics; compose only the approved domains needed for a selected question. Start with PostgreSQL read models and the existing service architecture. Add a separate analytical store, message broker, microservices, semantic engine, or workflow engine only after a measured need and an approved design. Any future AI capability must satisfy Evidence Before Answers and support customer-controlled local/on-prem inference; no model or inference runtime is selected or implemented. The detailed domain map and decision lifecycle are in [`TARGET_DOMAIN_ARCHITECTURE.md`](TARGET_DOMAIN_ARCHITECTURE.md).

### 6. How should financial intelligence evolve without inventing finance policy?

M8 is a sound **evidence and policy-gate pattern**, not an implemented finance engine. The target is optional **company-wide Financial Intelligence** across the selected Company’s finance domain—not merely project evaluation—while the current one-company-per-tenant boundary remains. Build it only after a named finance/accounting owner approves the relevant source contracts, facts, definitions, periods, units, currency/FX handling, precision/rounding, missing-data behavior, and policy versions. Until then preserve exact source observations and report `incomplete`; do not calculate, rank, forecast, or infer. AI/LLMs never become calculation truth. See [`FINANCIAL_INTELLIGENCE_ARCHITECTURE.md`](FINANCIAL_INTELLIGENCE_ARCHITECTURE.md).

### 7. What is the recommended next implementation milestone and what is excluded from its MVP?

**No implementation is authorized by M9, and the broader target is not ready to implement without owner/domain decisions.** The recommended next *candidate* implementation milestone, only after explicit approval, is an unnumbered **Company-Level Governed Data Vertical Slice**: one selected domain, one owner-defined source/data contract, and one read-only company-level report or decision question. Reuse M4 staging/traceability, M5 deterministic snapshots where applicable, and the existing authorization/RLS patterns. If Finance selects the first domain, the initial slice may store and inspect approved source observations, but it must emit no financial calculation or verdict until exact policy and tests are approved. Do not invent a domain, source schema, formula, threshold, or company hierarchy in advance.

Preconditions are: a product owner selects the initial decision and users; the domain owner identifies authoritative source fields and correction/freshness policy; Finance approves any financial semantics before calculation; and security/operations owners review retention and access. If these choices are not made, the next step is domain discovery and approval—not code.

The first MVP should **exclude** all-domain coverage, multi-company consolidation, a universal KPI/schema/workflow engine, broad live connectors, a data warehouse, arbitrary SQL, unapproved accounting/FX/rounding/forecasting rules, generated financial numbers, autonomous recommendations or actions, external writes, outcome/causal claims, and a polished all-purpose BI workbench. A minimal experience necessary to validate the selected vertical slice can be scoped separately. No M10 or other implementation milestone is authorized by this assessment.
