# AUVRA Phase 1 Reuse Register

- **Assessment date/cutoff:** 2026-11-21 (UTC).
- **Scope:** Internal BFS code reuse and external OSS screening for the accepted API-only Operations Intelligence proof.
- **Decision status:** Engineering classification for the accepted Phase 1 scope. Local verification passed 475 PostgreSQL-backed tests and a separate 17-test focused Operations run, repository Ruff format/lint, mypy, Alembic parity, final `git diff --check`, and focused implementation/security review. PR #41 and push CI passed on the reviewed head; post-merge `main` CI passed on the merge commit. The bounded engineering scope is closed; owner decisions for customer, KPI, sensitive-data, and production uses remain separate. This is not legal approval, production approval, or a complete SBOM/security audit; see [`PHASE1_ACCEPTANCE_REPORT.md`](PHASE1_ACCEPTANCE_REPORT.md).
- **Classification vocabulary:** Reuse the established categories from [`OPENFPA_TECHNICAL_REUSE_AUDIT.md`](OPENFPA_TECHNICAL_REUSE_AUDIT.md): **REUSE DIRECTLY**, **ADAPT**, **BFS-NATIVE IMPLEMENTATION**, **DESIGN INSPIRATION ONLY**, **DEFER**, and **REJECT**.

## Internal BFS reuse register

| Existing component | Classification | Phase 1 decision and boundaries |
|---|---|---|
| Tenant/Company authorization, `require_company_context_access`, transaction-local context, forced RLS, runtime/migrator split | **REUSE DIRECTLY** | Preserve the working security boundary. Add only narrowly scoped Operations permissions and new forced-RLS tables. Never accept tenant/company authority from request JSON. |
| Universal Data sources, profiles, source revisions, validation, promotion, lineage, and retention | **ADAPT** | Reuse existing source registration and exact revision IDs as evidence references. A registration, manual source, or successful import does not prove authority/accuracy/completeness. Do not change the immutable `1.0.0`/`1.1.0` contracts, purge behavior, or raw-data permission boundary for this slice. |
| `business_activity` and `operational_record` canonical entities | **ADAPT** | Link exact source revisions when a human asserts an operational interpretation. Do not reinterpret generic record fields as lifecycle transitions or infer a work-item state. |
| `metrics.snapshot.content_hash`, deterministic calculation style, immutable input/result snapshots, replay patterns | **REUSE DIRECTLY** | Reuse canonical JSON hashing and bounded deterministic application calculation. Keep calculation logic separate from persistence. |
| Current Business Intelligence registry/engine/analysis API | **ADAPT** | Reuse metric governance and snapshot patterns; do not duplicate its generic formula engine. The existing operations catalog only counts source activity/record rows; the new Operations event observation contract stays a bounded domain-owned calculation. |
| M7 `project_decisions` and human approval model | **DESIGN INSPIRATION ONLY** | Retain its immutable evidence binding, versioning, optimistic concurrency, and separated human authority as patterns. It is project-specific; do not generalize or rename it without an explicit Operations decision/approval use case. |
| Universal Data manual assertions/correction history and the customer-commitment event hash pattern | **ADAPT** | Reuse append-only version and actor-attribution principles; keep Operations fields and rules domain-owned. Do not copy customer terminology, required fields, evidence file types, process transitions, or retention assumptions. |
| Existing frontend/static pages and visualization assets | **REJECT for Phase 1 scope** | No UI/UX work is authorized. Keep Phase 1 backend/API-only. |
| Distributed services, event broker, warehouse/lakehouse, workflow engine, AI/vector store, solver | **DEFER** | No measured need or approved use case justifies adding them. PostgreSQL and the modular monolith remain sufficient for the bounded slice. |

## External candidates — cutoff screen and decision

The detailed release, license, compatibility, dependency, and advisory observations are in [`../OPEN_SOURCE_INVENTORY.md`](../OPEN_SOURCE_INVENTORY.md), section “AUVRA Phase 1 candidate screen (2026-11-21 cutoff).” Exact release pins are screening references, not approved dependencies.

| Candidate/use | Phase 1 classification | Why it is not adopted now |
|---|---|---|
| Hypothesis — property-based tests | **DEFER** | The new domain can be verified with deterministic generated fixtures and direct invariant tests without adding a test dependency. Exact screened pin `6.170.17` uses MPL-2.0 source (with exceptions) and a direct `sortedcontainers<3,>=2.1` dependency; transitive legal/resolved footprint has not been cleared. Revisit only if a concrete property-test need remains after ordinary unit/DB tests. |
| Pandera / Frictionless — table validation and file contracts | **REJECT for this slice** | BFS already owns explicit CSV/XLSX parsing, typed Pydantic contracts, row-level validation, quarantine, immutable evidence, and PostgreSQL persistence. Pandera adds Pydantic/typeguard/typing-inspect dependencies; Frictionless has a substantially broader table/file dependency graph and overlaps import behavior. No missing capability or benchmark justifies parallel validators. |
| Polars / DuckDB — batch transformation/analytics | **DEFER** | There is no measured import or analysis bottleneck. Polars brings a native runtime wheel; DuckDB is a large native wheel and extension-specific licenses/security need review. Neither becomes a primary transactional store or authority. |
| OpenLineage — interoperable data lineage | **DEFER** | Existing provenance is already source-, row-, revision-, and run-scoped inside BFS. No external lineage consumer or interchange requirement is established. |
| SQLGlot — SQL parser/AST | **REJECT for Phase 1** | Arbitrary SQL is explicitly out of scope. The simple fixed Operations calculation does not need an SQL parser; accepting arbitrary SQL would broaden attack and governance surfaces. |
| OpenMetadata ingestion — metadata/connectors | **REJECT pending legal/service-model review** | Exact PyPI `openmetadata-ingestion==2.1.0.1` metadata declares the Collate Community License Agreement; exact `ingestion/LICENSE` excludes competing SaaS/PaaS/IaaS/similar online services. The package declares a broad connector/cloud dependency surface (48 base `Requires-Dist` entries; 23.7 MB wheel). Root repository Apache metadata does not clear the ingestion package. No legal clearance or connector need exists. |
| Dagster — orchestration | **DEFER** | The monolith has no approved scheduled workflow need. Core `1.13.31` is Python-compatible and Apache-2.0 at the exact tag, but declares 31 direct base requirements and creates orchestration/operations overhead. Reviewed core advisories are version-range-specific and patched before this pin; connector integration versions must be screened separately if ever selected. |
| dbt Core — warehouse transformations | **DEFER** | No external warehouse/model lifecycle is selected. `1.12.7` is compatible with Python and Apache-2.0 at the exact tag, but declares 25 direct base dependencies and a larger transitive adapter/metric stack. Its `sqlparse` range is not pinned; 2026 advisories make a resolved lockfile and patched transitive version mandatory before any future adoption. |
| SQLMesh — warehouse transformation/orchestration | **DEFER** | No separate warehouse, scheduling service, or model deployment need has been measured. It brings a larger dependency surface including DuckDB/Pandas and adds a second orchestration/runtime boundary. |
| Apache Superset — dashboard product | **REJECT for Phase 1 scope** | UI/UX is explicitly excluded. The 6.1.0 package is Apache-2.0 at the release tag but declares a broad Flask/Celery/database-driver footprint and a ~104 MB wheel. It cannot replace BFS authorization, metric definitions, or decision authority. |

### Candidate adoption gate

No source code, image, dependency, or candidate runtime is selected. If a concrete need emerges, require the exact package and source commit/tag, PyPI metadata, path-level licenses/notices, resolved lockfile/SBOM, vulnerability/advisory ranges and patch versions, Python/database compatibility, maintenance/support review, overlap analysis, an adapter boundary, upstream tests, BFS-specific security/correctness tests, and product/legal/security approval **before** adding it. Empty advisory-search results are not proof of no vulnerabilities.
