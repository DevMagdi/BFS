## BI ingestion-pointer retention finding — purge behavior unchanged

Source inspection reconfirmed the PR #39 investigation:

1. `analysis_service.py` saves source-selection/candidate metadata (`latest_ingestion_id`, `last_promoted_ingestion_id`) in immutable BI input snapshots. The selected canonical-record evidence separately stores actual ingestion/source-row references.
2. Saved BI replay recalculates from the saved definition/config/input snapshots; evidence listing and report rendering read saved evidence. They do not dereference metadata-only ingestion pointers. A new readiness check/analysis is live-source work, not saved-run replay.
3. `retention.py::build_purge_plan` checks canonical revisions, canonical ingestion links, semantic mapping dependencies, and the original source snapshot. The `businessflow_purge_universal_ingestions` SQL function in migration `0028` rechecks canonical revisions/links and only deletes an original snapshot when it has no remaining ingestion or revision reference. Neither path inspects BI JSON pointer fields.
4. Therefore a metadata-only pointer can outlive its live ingestion (and an unshared original source snapshot) if the ingestion has no protected canonical dependencies. The tombstone retains the ingestion UUID, idempotency-key hash, policy version, actor, and purge time, not source/ingestion payload. The saved run remains replayable from its own snapshot, but consumers cannot rely on resolving every metadata pointer afterward.

This is an unresolved BI/source-evidence and Universal Data retention-owner decision, not authorization to pin or purge those pointers. Decide separately whether selected-source pointers, unselected candidate pointers, both, or neither are retention dependencies and what post-purge audit evidence is required. Until an accountable owner decides, keep current purge behavior and tombstone unchanged; do not claim the tombstone reconstructs purged details.
